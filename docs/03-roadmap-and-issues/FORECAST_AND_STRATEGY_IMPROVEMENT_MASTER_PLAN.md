## 0. دستور صریح به عامل پیاده‌سازی (Gemini)

این سند صرفاً فهرست ایده یا پیشنهاد UX نیست؛ نقشه راه مهندسی برای اصلاح انحراف Forecast و Strategy است. عامل پیاده‌سازی باید آن را همراه اسناد مرجع بخواند و دقیقاً بر اساس قراردادها و ترتیب فازهای آن کار کند.

**ممنوع است که عامل صرفاً چند کارت UI اضافه کند، نام مدل‌ها را جابه‌جا کند یا یک الگوریتم جدید به سیستم اضافه کند و کار را تمام‌شده اعلام کند.** مسئله اصلی، نبود سلسله‌مراتب تصمیم، نبود سنجش کامل کیفیت مسیر، و نبود قرارداد روشن بین تشخیص بازار، پیش‌بینی و تصمیم قابل اقدام است.

### 0.1. ترتیب تقدم اسناد

در صورت تعارض، تقدم به این ترتیب است:

1. `FORECAST_PRODUCT_FOUNDATION_V1.md` برای مأموریت محصول و کیفیت خروجی مورد انتظار؛
2. `FORECAST_SYSTEM_SPEC_V1.md` برای چرخه عمر، قراردادهای سیستمی، داده، زمان و ارزیابی؛
3. این سند برای راهکار اجرایی و اولویت‌بندی اصلاحات Forecast/Strategy؛
4. `FORECAST_ACCEPTANCE_TEST_PLAN_V1.md` برای آزمون و معیار پذیرش؛
5. اسناد تخصصی مدل، MTF، Strategy و معماری برای جزئیات همان حوزه.

این سند حق ندارد مأموریت Product Foundation را تغییر دهد یا به‌صورت ضمنی الزام تازه‌ای را جایگزین آن کند. اگر تعارض واقعی پیدا شد، آن را گزارش کن و سند بالادستی را خودسرانه تغییر نده.

### 0.2. ممنوعیت‌های قطعی در اجرای پروژه

- منبع فعال داده بازار فقط **TradingView** است. هیچ Provider دیگری را برای Forecast یا Strategy فعال، جایگزین یا به‌عنوان fallback اضافه نکن.
- هیچ Cron، زمان‌بندی خودکار، polling پس‌زمینه یا اجرای دوره‌ای اضافه نکن. محاسبه فقط با درخواست کاربر و Refresh/اجرای دستی انجام شود.
- محیط Production روی هاست اشتراکی است: اجرای Python، فرایند خارجی، shell، `exec()`، Worker سمت سرور یا وابستگی به سرویس Python مجاز نیست.
- Runtime جدید باید در مرورگر و با JavaScript سازگار با معماری فعلی اجرا شود. Web Worker مرورگر فقط در صورت سازگاری واقعی با ساختار فعلی مجاز است؛ آن را با Worker یا پردازش سمت سرور اشتباه نگیر.
- هیچ درخواست شبکه، مصرف API، یا پردازش سنگین پنهان و خودکار اضافه نکن.
- هیچ داده ساختگی، OHLC ساختگی، حجم جعلی، نویز تصادفی، موج تزئینی، احتمال ساختگی یا سناریوی بدون شواهد تولید نکن.
- هیچ مدل یا موتور جدیدی صرفاً برای پرکردن Registry اضافه نکن.
- نتیجه تست نرم‌افزاری، موفقیت اجرای مدل یا ظاهر طبیعی نمودار را به‌عنوان اثبات برتری پیش‌بینی معرفی نکن.
- منطق فعلی Strategy کلاسیک و Hard Gate معتبر آن را صرفاً برای افزایش تعداد سیگنال‌ها تضعیف نکن.
- هیچ اتصال Broker، سفارش واقعی یا اجرای معامله اضافه نکن.
- اسناد مرجع را با افزودن وصله‌های انتهایی و بدون اصلاح محل مرتبط به‌روز نکن.

### 0.3. محدوده اختیار

این سند مجوز طراحی و برنامه‌ریزی است. هر فاز کدنویسی باید طبق دستور مستقیم مالک پروژه اجرا شود. عامل نباید به بهانه این سند دامنه کار را به بازنویسی کامل برنامه، تغییر Provider، تغییر ساختار داده یا افزودن قابلیت‌های خارج از Scope گسترش دهد.

## 1. تشخیص مسئله و تعریف هدف نهایی

### 1.1. تشخیص مسئله

گزارش ممیزی مبنای این برنامه، وضعیت مرجع `v1.47.41` را چنین توصیف می‌کند:

- چند خانواده مدل و موتور پیش‌بینی به‌صورت موازی در دسترس‌اند؛
- AUTO و انتخاب برنده به معیارهای سخت OOS وابسته‌اند و در بسیاری از موارد ممکن است به Baseline برگردند؛
- جزئیات تحقیقاتی متعدد در UI حضور دارند، اما کاربر پاسخ تصمیم‌محور واحدی دریافت نمی‌کند؛
- کیفیت مسیر، نقاط عطف و رفتار بازار باید در کنار خطای قیمت ارزیابی شوند؛
- Forecast و Strategy دو زیرسیستم مستقل‌اند و قرارداد کنترل‌شده‌ای برای استفاده Strategy از Forecast وجود ندارد.

این موارد **گزارش ممیزی و ادعاهای ثبت‌شده در زمان تهیه گزارش‌اند**. پیش از هر تغییر کد، وضعیت جاری باید با فایل‌ها و تست‌های همان شاخه بررسی شود. اعداد و قابلیت‌های ثبت‌شده در گزارش، بدون راستی‌آزمایی مجدد نباید به‌عنوان وضعیت قطعی کد فعلی بازگو شوند.

### 1.2. هدف محصول

هدف، تبدیل Forecast به یک **سامانه قابل فهم برای توصیف و ارزیابی رفتار احتمالی قیمت** است؛ نه نمایشگاه مدل‌ها و نه مولد خطوط آینده.

سیستم باید بتواند در یک مبدأ زمانی مشخص و با داده مجاز همان لحظه:

1. وضعیت و زمینه بازار را تشخیص دهد؛
2. مسیر محتمل قیمت را در طول افق پیش‌بینی ارائه کند؛
3. حرکت‌های اصلی، اصلاح‌ها، سقف‌ها، کف‌ها و نقاط چرخش احتمالی را تا حدی که شواهد اجازه می‌دهد مشخص کند؛
4. عدم‌قطعیت را صادقانه و با کالیبراسیون قابل سنجش نمایش دهد؛
5. خروجی را ثبت کند تا بعداً با واقعیت مقایسه شود؛
6. در صورت نبود شواهد کافی، صریحاً از ادعای برتری یا تولید سیگنال خودداری کند.

**اولویت محصول:** رفتار و کیفیت مسیر ← اعتبارسنجی و ثبت ← تصمیم واحد و UX ← اتصال کنترل‌شده به Strategy. تعداد مدل‌ها اولویت نیست.

### 1.3. تعریف موفقیت

یک تغییر فقط وقتی موفق است که هم‌زمان:
- قرارداد داده و زمان را حفظ کند؛
- رفتار پیش‌بینی را بهتر یا قابل‌ارزیابی‌تر کند؛
- معیار پذیرش مربوط به خود را پاس کند؛
- در UI نتیجه و محدودیت را درست منتقل کند؛
- مستندات و تست‌ها به‌روز شده باشند؛
- روی هاست اشتراکی و مرورگر واقعی قابل اجرا باشد.

## 2. معماری هدف: چهار لایه با مسئولیت‌های جدا

معماری هدف باید چهار مسئولیت مستقل داشته باشد. این تفکیک برای جلوگیری از تکرار خطای فعلی ضروری است.

```
TradingView candles (closed-bar, timestamped)
                  |
                  v
       1. Market Context & Structure
                  |
                  v
       2. Forecast Models / Path Engine
                  |
                  v
       3. Decision & Evidence Layer
                  |
          +-------+--------+
          |                |
          v                v
     Simple UI        Research UI
          |
          v
  4. Optional Strategy Bridge
          |
          v
  Existing Classical Strategy Engine
```

### لایه 1 — Market Context & Structure

وظیفه: توصیف شرایط قابل مشاهده بازار با محاسبات علّی و قابل ممیزی.

این لایه پیش‌بینی آینده نیست و نباید برچسب‌های احتمالی خود را به‌عنوان واقعیت قطعی نمایش دهد.

### لایه 2 — Forecast Models / Path Engine

وظیفه: تولید مسیر قیمت و در صورت پشتیبانی معتبر، توزیع/باند عدم‌قطعیت و سناریوهای جایگزین.

هر مدل باید مستقل، نسخه‌دار، قابل مقایسه و قابل رد شدن باشد. مدل‌ها مالک UI و تصمیم نهایی نیستند.

### لایه 3 — Decision & Evidence

وظیفه: بررسی آمادگی داده، کفایت شواهد، وجود یا عدم وجود Edge، انتخاب مسیر اصلی و توضیح چرایی انتخاب.

این لایه تنها مرجع UI برای وضعیت نهایی Forecast است. UI نباید منطق انتخاب را دوباره پیاده کند.

### لایه 4 — Strategy Bridge اختیاری

وظیفه: تبدیل خروجی Forecast به ورودی محدود و قابل ممیزی برای موتور Strategy؛ فقط پس از عبور از گیت‌های سخت. این پل نباید استقلال Strategy کلاسیک را از بین ببرد.

## 3. قرارداد ورودی مشترک و سلامت داده

قبل از هر تحلیل یا اجرای مدل، یک قرارداد ورودی واحد و immutable ساخته یا از قرارداد معتبر فعلی استفاده شود. عامل نباید برای هر مدل برداشت متفاوتی از داده و زمان داشته باشد.

حداقل اطلاعات ورودی:

| فیلد | الزام |
|---|---|
| `symbol / instrumentId` | هویت دقیق سری TradingView؛ نمادهای مشابه یا مشتق‌شده قابل ادغام نیستند |
| `timeframe` | تایم‌فریم واقعی نمودار |
| `originTimestamp` | زمان آخرین کندل بسته‌شده مبنای پیش‌بینی |
| `lastClosedBar` | آخرین کندل مجاز برای پیش‌بینی |
| `dataSource` | فقط TradingView |
| `candles` | تاریخچه مرتب‌شده، بدون duplicate و با OHLC معتبر |
| `session/calendar` | تقویم و سشن متناسب با ابزار |
| `horizon` | تعداد کندل آینده و معنای زمانی آن |
| `dataQuality` | gap، داده ناقص، stale و محدودیت‌های تاریخچه |
| `contextTimeframes` | فقط تایم‌فریم‌های واقعاً موجود و هم‌تراز |

### 3.1. قواعد زمانی و علّی

- پیش‌فرض پیش‌بینی و ارزیابی، آخرین کندل بسته‌شده است.
- کندل در حال تشکیل نباید ناخواسته وارد ورودی مدل یا محاسبه Feature شود.
- تمام Featureها، سوئینگ‌ها، نواحی و رویدادها باید فقط از اطلاعاتی استفاده کنند که در زمان مبدأ قابل مشاهده بوده‌اند.
- هر سوئینگ باید زمان تشکیل و زمان تأیید جداگانه داشته باشد. سوئینگ تأییدنشده نباید در گذشته به‌گونه‌ای نمایش داده شود که انگار در همان لحظه قابل تشخیص بوده است.
- MTF باید با Timestamp و نسبت زمانی واقعی هم‌تراز شود؛ صرفاً یکسان بودن تعداد ردیف‌ها کافی نیست.
- داده‌های نماد، منبع، تایم‌فریم یا قرارداد متفاوت نباید برای افزایش تعداد نمونه با هم مخلوط شوند.
- در نبود تاریخچه کافی، داده نامعتبر یا مبدأ نامشخص، موتور باید پیش از اجرای مدل متوقف و علت را برگرداند.

### 3.2. وضعیت‌های Data Readiness

حداقل وضعیت‌های قابل تشخیص:
- `DATA_NOT_READY`: داده یا ورودی معتبر وجود ندارد.
- `INSUFFICIENT_HISTORY`: تاریخچه برای حداقل نیاز مدل/ارزیابی کافی نیست.
- `STALE_DATA`: آخرین داده نسبت به قواعد ابزار/سشن به‌روز نیست.
- `DATA_GAP`: شکاف یا ناسازگاری زمانی مؤثر وجود دارد.
- `READY`: ورودی برای اجرای مدل معتبر است.

این وضعیت‌ها را با `NO_EDGE` اشتباه نگیرید. نبود داده با نبود مزیت پیش‌بینی یک مسئله متفاوت است.

## 4. Market Context & Structure Engine

این لایه باید مشترک و مستقل از مدل پیش‌بینی باشد. خروجی آن مجموعه‌ای از مشاهدات قابل استناد است، نه یک امتیاز جادویی یا یک برچسب کلی مثل Bullish.

### 4.1. اجزای موردنیاز

| حوزه | خروجی‌های مورد انتظار | ملاحظات |
|---|---|---|
| Trend | جهت، قدرت، شیب، تداوم و تضعیف روند | تعریف محاسباتی نسخه‌دار؛ نه صرفاً رنگ سبز/قرمز |
| Swings | سقف/کف محلی، درجه اهمیت، زمان وقوع و تأیید | بدون look-ahead؛ زمان تأیید جداگانه |
| Structure | BOS، CHoCH، HH/HL/LH/LL | تعریف دقیق شکست و بافر لازم؛ جلوگیری از برچسب‌گذاری پس‌نگر |
| Regime | Trend، Range، Expansion، Compression و Unknown | همراه با confidence/evidence و امکان Unknown |
| Volatility | ATR، realized range، volatility expansion/contraction | مقیاس و پنجره زمانی ثبت شود |
| Momentum | شتاب/کاهش شتاب و واگرایی‌های تعریف‌شده | ویژگی مشتق‌شده؛ نه سیگنال قطعی |
| Levels | حمایت/مقاومت و نواحی عرضه/تقاضا | منبع، محدوده، زمان ایجاد، تعداد برخورد و اعتبار |
| Liquidity | EQH/EQL، FVG، POC/VAH/VAL در صورت وجود داده معتبر | نبود حجم واقعی نباید با حجم ساختگی جبران شود |
| Session | سشن و وضعیت باز/بسته بازار | رعایت DST و تقویم ابزار |
| MTF | زمینه تایم‌فریم بالاتر/پایین‌تر | اختلاف جهت الزاماً تناقض نیست |

### 4.2. قرارداد هر مشاهده

هر مشاهده ساختاری باید حداقل این فیلدهای مفهومی را داشته باشد:

```js
{
  type: "SWING_HIGH | BOS | CHOCH | SUPPORT_ZONE | ...",
  direction: "BULLISH | BEARISH | NEUTRAL",
  priceLevel: null,
  priceRange: null,
  occurredAt: 0,
  confirmedAt: 0,
  sourceTimeframe: "H1",
  methodId: "swing-pivot",
  methodVersion: "1.0.0",
  evidence: [],
  confidence: null,
  status: "ACTIVE | INVALIDATED | UNCONFIRMED"
}
```

این صرفاً قرارداد مفهومی است؛ قبل از پیاده‌سازی باید با الگوهای نام‌گذاری و ساختار موجود در Repository تطبیق داده شود. فیلد `confidence` اختیاری است و اگر کالیبره نشده، باید null بماند.

### 4.3. قواعد جلوگیری از خطای رایج

- Swing pivot را در زمان وقوع شناسایی‌شده فرض نکن؛ تا زمان تأیید، `UNCONFIRMED` است.
- BOS/CHoCH باید تعریف صریح شکست، منبع سطح و کندل تأیید داشته باشد.
- FVG، EQH/EQL یا Order Block را بدون قواعد دقیق تشکیل و invalidation اضافه نکن.
- هر ناحیه باید عمر، شرایط ابطال و منبع شواهد داشته باشد.
- یک Feature را چند بار با نام‌های متفاوت به موتورهای مختلف تزریق نکن؛ Feature registry مشترک و نسخه‌دار لازم است.
- در صورت نبود داده لازم، مقدار جعلی یا تخمینی را به‌جای مقدار واقعی وارد نکن؛ وضعیت `UNAVAILABLE` برگردان.

## 5. Forecast Path Engine: از خط آینده به مسیر قابل سنجش

### 5.1. قرارداد مسیر

Forecast اصلی باید مجموعه نقاط مرتب زمانی باشد. در فاز فعلی، Close-path کافی است؛ تولید OHLC کامل اجباری نیست و تا زمانی که مدل واقعاً توان تولید معتبر آن را ندارد، نباید شبیه‌سازی شود.

حداقل قرارداد مفهومی:

```js
{
  origin: { timestamp, close, symbol, timeframe },
  horizonBars: 30,
  points: [
    { step: 1, timestamp: 0, q50: 0, q10: null, q90: null }
  ],
  pathSemantics: "MARGINAL_MEDIAN | JOINT_TRAJECTORY",
  modelId: "model-id",
  modelVersion: "x.y.z",
  provenance: {},
  limitations: []
}
```

نکته حیاتی: Quantileهای نقطه‌ای در هر افق لزوماً یک مسیر مشترک نمونه‌گیری‌شده نیستند. اگر Q50 هر گام کنار هم قرار می‌گیرد، باید آن را مسیر میانه نقطه‌ای نامید؛ نباید بدون مدرک، آن را یک trajectory مشترک یا سناریوی دارای وابستگی زمانی معرفی کرد.

### 5.2. کیفیت مسیر، معیار درجه اول

فقط MAE انتهای افق یا Directional Accuracy کافی نیست. ارزیابی باید حداقل چهار محور مستقل داشته باشد:

**الف) خطای قیمت و توزیع**
- MAE / RMSE در هر گام و کل افق؛
- مقایسه با Naive در مقیاس یکسان؛
- WIS یا معیار مناسب کوانتایل؛
- پوشش باندها در سطح اسمی و تفکیک‌شده بر اساس افق؛
- عرض باند و Sharpness در کنار Coverage، تا باند بسیار عریض پاداش نگیرد.

**ب) ساختار مسیر**
- Swing High / Swing Low detection agreement؛
- خطای قیمت و زمان نقاط چرخش؛
- تعداد نقاط چرخش کاذب و ازدست‌رفته؛
- شباهت توالی موج‌ها و جهت قطعات مسیر؛
- خطای عمق اصلاح؛
- خطای مدت اصلاح/رنج؛
- خطای دامنه حرکت و دامنه نوسان؛
- حفظ ترتیب زمانی رویدادهای اصلی.

**ج) رفتار بازار**
- تشخیص Trend Continuation؛
- Pullback و عمق/مدت آن؛
- Range Formation و خروج از رنج؛
- Breakout و False Breakout؛
- Retest؛
- Reversal و تأخیر تشخیص؛
- واکنش به ناحیه حمایت/مقاومت.

**د) پایداری و قابلیت تعمیم**
- تفکیک نتایج بر اساس نماد، تایم‌فریم، افق و رژیم؛
- عملکرد در دوره‌های پرنوسان و کم‌نوسان؛
- حساسیت به طول تاریخچه و تغییر پارامتر؛
- پایداری Prefix-Invariance و MTF؛
- مقایسه با Baseline مناسب و جلوگیری از برتری ظاهری ناشی از نمونه‌های آسان.

### 5.3. پروتکل ارزیابی

- از Rolling/Walk-Forward با مبدأهای تاریخی متعدد استفاده شود.
- در هر مبدأ، فقط داده‌های قبل از آن مبدأ مجاز است.
- برای هر پیش‌بینی، افق، نماد، تایم‌فریم، نسخه مدل، پارامترها و شناسه Fixture ثبت شود.
- Purge و Embargo متناسب با افق و هم‌پوشانی برچسب‌ها اعمال شود.
- انتخاب مدل، تنظیم پارامتر و ارزیابی نهایی نباید روی یک بازه واحد انجام شوند.
- یک Final Untouched Holdout تا زمان تصمیم پذیرش دست‌نخورده باقی بماند.
- مدل و Naive باید روی originها، horizonها و actualهای یکسان مقایسه شوند.
- معیارهای میانگین به‌تنهایی کافی نیستند؛ توزیع عملکرد و بدترین زیرگروه‌ها نیز گزارش شود.
- اگر تعداد نمونه مؤثر کم است، نتیجه `INSUFFICIENT_EVIDENCE` است؛ کمبود نمونه را با کاهش دلخواه آستانه‌ها پنهان نکن.
- گزارش باید تعداد پنجره، تعداد نمونه مؤثر، پوشش زمانی و محدودیت‌ها را درج کند.

### 5.4. Baselineها

حداقل Baseline اجباری `naive_persistence` است. در صورت تناسب داده، Baselineهای ساده دیگر مانند drift یا seasonal-naive می‌توانند در پروتکل آزمون تعریف شوند؛ اما تعریف و انتخاب آن‌ها باید قبل از مشاهده نتیجه ثبت شود.

هیچ مدلی صرفاً به دلیل بهتر بودن از یک Baseline ضعیف، برنده محسوب نمی‌شود. مدل باید از Baseline مرتبط و از نظر پیچیدگی/هزینه توجیه‌پذیر باشد.

### 5.5. رویدادهای مسیر و سناریوها

رویدادهای ساختاریافته فقط در صورت وجود تعریف قابل آزمون تولید شوند؛ مانند:
- `TREND_CONTINUATION`
- `PULLBACK`
- `RESISTANCE_TEST`
- `SUPPORT_REACTION`
- `BREAKOUT`
- `RETEST`
- `RANGE_FORMATION`
- `REVERSAL`

هر رویداد باید زمان یا بازه مورد انتظار، ناحیه قیمت، جهت، شرط تحقق، شرط ابطال، شواهد و منبع خود را داشته باشد. رویداد مشتق‌شده از Market Structure باید از رویداد تولیدشده توسط خود مدل قابل تفکیک باشد.

سناریوهای Base / Alternative / Invalidation فقط وقتی مجازند که:
- مسیرها از نظر رفتار یا شرط وقوع واقعاً متفاوت باشند؛
- منبع و روش تولید مشخص باشد؛
- احتمال عددی فقط در صورت کالیبراسیون معتبر ارائه شود؛
- سناریوی جایگزین صرفاً نسخه تصادفی یا جابه‌جایی بصری مسیر اصلی نباشد.

## 6. Decision Layer: یک مرجع واحد برای نتیجه Forecast

### 6.1. مسئولیت

یک تابع/ماژول مرکزی با نام مفهومی `buildDecisionSummary(forecastResult, evidence, context)` ایجاد شود. نام نهایی باید با الگوی Repository هماهنگ باشد.

این ماژول باید:
1. اعتبار ورودی و خروجی را کنترل کند؛
2. کفایت شواهد ارزیابی را بررسی کند؛
3. نتیجه Strict OOS را بخواند؛
4. در صورت نبود برنده Strict، امکان نمایش بهترین نسبی را فقط با قواعد محدود بررسی کند؛
5. مسیر اصلی و علت انتخاب را مشخص کند؛
6. مجاز بودن یا نبودن Strategy Bridge را تعیین کند؛
7. یک خروجی ثابت و قابل مصرف برای UI ارائه کند.

UI حق ندارد این منطق را با if/elseهای پراکنده دوباره بسازد.

### 6.2. Schema مفهومی

```js
{
  status: "DATA_NOT_READY | INSUFFICIENT_EVIDENCE | NO_EDGE | PROVISIONAL | VALID",
  edgeStatus: "PROVEN | NOT_PROVEN | UNKNOWN",
  selectionMode: "MANUAL | AUTO_STRICT | AUTO_RELATIVE | BASELINE",
  primaryPath: null,
  modelId: "naive_persistence",
  modelVersion: null,
  confidence: "LOW | MEDIUM | HIGH | null",
  reasonCode: "NO_STRICT_WINNER | BETTER_THAN_BASELINE | ...",
  reasonText: "",
  evidenceSummary: {},
  allowStrategy: false,
  strategyBlockReason: null,
  warnings: []
}
```

این Schema هدف مفهومی است. مقادیر موجود در سیستم را حفظ و با قراردادهای فعلی تطبیق بده؛ برای سازگاری، فیلدهای قدیمی را بدون بررسی مصرف‌کنندگان حذف یا rename نکن.

### 6.3. معنای وضعیت‌ها

| وضعیت | معنی دقیق | مسیر قابل نمایش | Strategy از مسیر Forecast |
|---|---|---|---|
| `DATA_NOT_READY` | داده/ورودی معتبر نیست | مسیر پیش‌بینی نمایش داده نشود؛ در صورت نیاز آخرین داده واقعی | ممنوع |
| `INSUFFICIENT_EVIDENCE` | داده اجرای مدل موجود است اما شواهد OOS کافی نیست | Baseline یا مسیر اکتشافی با برچسب محدودیت | ممنوع |
| `NO_EDGE` | آزمون معتبر انجام شده اما هیچ مدل برتری قابل قبول نسبت به Baseline ندارد | Baseline با برچسب «بدون Edge اثبات‌شده» | ممنوع |
| `PROVISIONAL` | یک گزینه نسبی/محدود وجود دارد اما معیار پذیرش علمی کامل نیست | مسیر با برچسب آشکار «نسبی، اثبات‌نشده» | ممنوع در حالت پیش‌فرض |
| `VALID` | تمام گیت‌های پذیرش سخت و شواهد کافی پاس شده‌اند | مسیر منتخب و عدم‌قطعیت کالیبره‌شده | فقط با عبور از گیت‌های Strategy |

قانون: `PROVISIONAL` مترادف «قابل معامله» نیست. نمایش مسیر موقت با اجازه تولید سیگنال یکسان نیست.

### 6.4. تصمیم‌گیری مرحله‌ای

```
Input readiness?
  NO -> DATA_NOT_READY
  YES
    |
Evidence sufficient?
  NO -> INSUFFICIENT_EVIDENCE + baseline display
  YES
    |
Strict OOS winner passes all frozen acceptance gates?
  YES -> VALID + strict winner
  NO
    |
Any eligible candidate beats baseline on pre-registered
relative criteria without material quality/calibration failure?
  YES -> PROVISIONAL + relative candidate
  NO -> NO_EDGE + baseline
```

این ترتیب باید در کد و تست‌ها یکسان باشد. وضعیت داده/شواهد نباید با نتیجه انتخاب مدل مخلوط شود.

### 6.5. AUTO Strict و AUTO Relative

**AUTO Strict**
- تنها مسیر اعطای `VALID` و پذیرش علمی است.
- آستانه‌ها باید از Acceptance Plan و سیاست مدل‌پذیری مصوب خوانده شوند؛ در چند فایل hard-code نشوند.
- تغییر آستانه برای افزایش تعداد برنده‌ها ممنوع است مگر با مطالعه اثر، ثبت نسخه سیاست و تست مستقل.
- p-value، bootstrap، تعداد نمونه مؤثر، Coverage و WIS باید در کنار هم و با تفسیر درست بررسی شوند.
- پاس شدن آستانه‌ها به‌تنهایی تضمین سودآوری نیست.

**AUTO Relative**
- فقط برای پاسخ UX به این پرسش است: «از بین گزینه‌های واجد شرایط، کدام یک نسبتاً بهتر است؟»
- خروجی آن همیشه `PROVISIONAL` و `edgeStatus: NOT_PROVEN` است.
- اگر کاندیدا در معیار اصلی کیفیت مسیر یا WIS از Baseline بدتر باشد، یا Calibration آن به‌طور معنادار نامعتبر باشد، انتخاب نسبی مجاز نیست؛ Baseline و `NO_EDGE` حفظ شود.
- صرف کمترین WIS در میان مدل‌های بد، برتری نسبی قابل نمایش ایجاد نمی‌کند.
- مقایسه باید روی داده، origin و horizon یکسان باشد.
- AUTO Relative هرگز به Strategy سیگنال قابل اقدام نمی‌دهد.
- در UI واژه «بهترین» بدون قید نسبی/اثبات‌نشده ممنوع است.

### 6.6. انتخاب دستی

اگر کاربر مدل مشخصی را انتخاب کند:
- اجرای همان مدل نمایش داده شود، مشروط به موفقیت فنی و اعتبار خروجی؛
- انتخاب دستی نباید وضعیت اعتبار علمی آن مدل را ارتقا دهد؛
- اگر مدل ارزیابی OOS معتبر ندارد، وضعیت شواهد همچنان `INSUFFICIENT_EVIDENCE` یا برچسب پژوهشی مناسب باقی بماند؛
- انتخاب دستی مجوز عبور از گیت Strategy نیست.

## 7. Model Governance و نقش مدل‌ها

### 7.1. اصل نقش‌محور

مدل‌ها باید بر اساس نقش و شواهد رتبه‌بندی شوند، نه شهرت الگوریتم یا پیچیدگی کد. هیچ مدل دائماً برنده فرض نمی‌شود؛ نتیجه باید بر اساس نماد، تایم‌فریم، افق و رژیم بازار گزارش شود.

### 7.2. دسته‌بندی اولیه برای بررسی

این دسته‌بندی از گزارش ممیزی استخراج شده و **فهرست پذیرش نهایی نیست**. پیش از استفاده، وضعیت واقعی هر شناسه در Registry و شواهد OOS آن بررسی شود.

| نقش | شناسه/مدل گزارش‌شده | سیاست هدف |
|---|---|---|
| Baseline اجباری | `naive_persistence` | همیشه در ارزیابی و fallback شفاف |
| مدل‌های ترجیحی برای ارزیابی عمیق | `empirical_analogs`، `structural_wave_js`، `smc_prediction_js` | نامزدهای اصلی Path Quality؛ نه برنده از پیش تعیین‌شده |
| مدل‌های آماری | `kalman_momentum`، `garch_volatility`، `arima_ets` / `native_arima_diff`، `historical_drift`، `gaussian_process` | امکان رقابت در صورت هم‌ترازی قرارداد و ارزیابی |
| Ensemble | `calibrated_ensemble` | فقط با وزن‌های منجمد و leakage-safe از Walk-Forward |
| Approximationهای گزارش‌شده | `native_prophet_decomp`، `native_seq_recurrent_approx`، `native_quantile_attention_approx` | Research-only تا زمان اثبات کیفیت و رفع محدودیت‌های ماهوی |

### 7.3. شرایط ورود به Decision Pool

هر مدل برای ورود به Decision Pool باید:
- قرارداد ورودی و خروجی یکسان را رعایت کند؛
- Prefix-Invariance و زمان‌بندی را پاس کند؛
- در برابر Baseline روی originهای یکسان ارزیابی شود؛
- مسیر، عدم‌قطعیت و محدودیت‌هایش درست برچسب بخورند؛
- حداقل شواهد موردنیاز برای نماد/تایم‌فریم/افق هدف را داشته باشد؛
- نسخه و پارامترهایش قابل بازتولید باشند.

مدل Research-only می‌تواند برای تحقیق اجرا شود، اما نباید در AUTO، کارت تصمیم یا Strategy ظاهر شود مگر اینکه Gate پذیرش را جداگانه پاس کرده باشد.

### 7.4. Ensemble

- وزن‌ها نباید با استفاده از همان پنجره‌ای که برای گزارش عملکرد Ensemble استفاده می‌شود تنظیم شوند.
- وزن‌ها باید از داده گذشته و فرایند Walk-Forward مجاز استخراج و سپس برای بازه آزمون freeze شوند.
- Ensemble نباید صرفاً به دلیل ترکیب چند مدل معتبر فرض شود.
- در صورت نبود وزن معتبر، Ensemble از Decision Pool خارج و صرفاً Research باقی بماند.

### 7.5. Lifecycle مدل

حداقل وضعیت‌ها:
`EXPERIMENTAL → CANDIDATE → ACCEPTED` و در صورت افت عملکرد `DEGRADED / SUSPENDED / RETIRED`.

تغییر وضعیت باید با گزارش شواهد، نسخه مدل، دامنه اعتبار (symbol/timeframe/horizon/regime) و تاریخ تصمیم ثبت شود.

## 8. UX هدف: Simple در برابر Research

### 8.1. Simple — پیش‌فرض

Simple باید در نگاه اول به پنج سؤال پاسخ دهد:
1. داده آماده است؟
2. آیا Edge اثبات‌شده داریم؟
3. مسیر اصلی چیست؟
4. کدام مدل/مبنا آن را تولید کرده؟
5. چرا این نتیجه انتخاب شده و چه محدودیتی دارد؟

اجزای مجاز:
- یک Decision Card در بالای صفحه؛
- یک مسیر اصلی Q50 یا مسیر مرکزی با نام‌گذاری صحیح؛
- یک باند عدم‌قطعیت معتبر (مثلاً 80%)، فقط اگر Calibration آن قابل دفاع است؛
- ۲ تا ۳ معیار کلیدی شامل کیفیت نسبی در برابر Baseline و وضعیت Coverage/Path Quality؛
- دلیل انتخاب و آخرین مبدأ/افق؛
- یک پیام واضح در صورت نبود Edge یا شواهد.

Simple نباید ده مسیر مدل را هم‌زمان روی چارت رسم کند. نمایش مسیر Baseline باید از مسیر مدل منتخب قابل تشخیص باشد.

### 8.2. Research — اختیاری

Research محل پنل‌های مقایسه، Walk-Forward، Quantiles، MTF، Analogs، Event Tree، Replay و Ledger است. این بخش نباید پیش‌فرض یا رقیب بصری Decision Card باشد.

- پنل‌ها به گروه‌های مشخص تقسیم شوند: Model Comparison، Path Quality، Calibration، Structure/Events، Replay/History، Diagnostics.
- هر نمودار باید عنوان، واحد، افق، نمونه و معنای معیار داشته باشد.
- جدول مقایسه فقط مدل‌های قابل مقایسه را کنار هم قرار دهد.
- مدل‌های Research-only با برچسب واضح مشخص شوند.
- وقتی وضعیت `NO_EDGE` است، جدول نباید با رتبه‌بندی ظاهراً قطعی، یک برنده مصنوعی بسازد.
- حالت Research باید بتواند همان پیش‌بینی ثبت‌شده در Simple را بررسی کند؛ محاسبه متفاوت یا تغییر پنهانی مبدأ ممنوع.

### 8.3. نمایش روی چارت

- در حالت Simple فقط یک مسیر اصلی و در صورت اعتبار یک باند نمایش داده شود.
- مبدأ و آخرین کندل واقعی به وضوح مشخص باشند.
- مسیر پیش‌بینی با کندل‌های واقعی اشتباه نشود.
- رخدادهای ساختاریافته با marker/annotation کم‌تعداد و قابل توضیح نمایش داده شوند.
- چارت نباید با چند رنگ و مسیر هم‌پوشان به ابزار تحقیقاتی شلوغ تبدیل شود.

### 8.4. تفکیک UI از منطق

منطق تصمیم باید در Decision Layer باشد. UI فقط render کند. `forecastView.js` را بدون شناخت وابستگی‌ها و تست‌ها یک‌باره بازنویسی نکن. اگر refactor لازم است، به اجزای کوچک با قراردادهای روشن تقسیم شود؛ اما refactor ظاهری بدون تست رفتار، تحویل محسوب نمی‌شود.

## 9. Strategy: حفظ استقلال، اصلاح ارزیابی، کنترل ریسک

### 9.1. اصل استقلال

Strategy کلاسیک باید مستقل و قابل استفاده باقی بماند. سیگنال‌های فعلی TA نباید به‌طور پنهان به خروجی Forecast وابسته شوند. Forecast و Strategy دو منبع شواهد متفاوت‌اند و باید provenance جدا داشته باشند.

### 9.2. قواعد موجودی که نباید تضعیف شوند

طبق اسناد فعلی Strategy:
- سیگنال بر اساس کندل بسته‌شده صادر می‌شود؛
- اجرای فرضی روی Open کندل بعدی انجام می‌شود؛
- Hard Gate `Net R:R ≥ 2.0` غیرقابل کاهش است؛
- SL باید ساختاری و واقع‌بینانه باشد؛
- TP1 باید نزدیک‌ترین مانع ساختاری معتبر باشد؛
- عبور از مانع نزدیک‌تر برای ساختن R:R جذاب‌تر ممنوع است؛
- Spread، Commission، Slippage و Swap باید در ارزیابی لحاظ شوند؛
- tie-breaker محافظه‌کارانه و قواعد جلوگیری از Chase/Duplicate حفظ شوند؛
- خروجی همچنان پژوهشی و شبیه‌سازی آفلاین است، نه اجرای زنده.

هر تغییر در این قواعد باید با اصلاح سند Strategy، تست اختصاصی و دلیل روشن انجام شود؛ صرف افزایش تعداد سیگنال‌ها دلیل کافی نیست.

### 9.3. شکاف اعتبارسنجی Strategy

Net R:R شرط لازم است، نه اثبات سودآوری. ارزیابی Strategy باید در کنار آن شامل موارد زیر باشد:
- Expectancy و Average R؛
- تعداد معاملات و کفایت نمونه؛
- Profit Factor و Win/Loss distribution؛
- Maximum Drawdown و مدت بازیابی؛
- توزیع نتایج در رژیم‌ها و نمادها؛
- حساسیت به هزینه‌های 1x، 1.5x و 2x یا سناریوهای هزینه مستند؛
- Walk-Forward و Final Untouched Holdout؛
- پایداری پارامترها و جلوگیری از انتخاب بهترین پارامتر با نگاه به کل تاریخچه.

Split ساده 70/30 به‌تنهایی کافی نیست. اگر در کد فعلی وجود دارد، آن را حذف نکن؛ آن را به‌عنوان گزارش پایه نگه دار و پروتکل Purged Walk-Forward + Embargo + Final Holdout را به‌صورت افزایشی و قابل مقایسه اضافه کن.

### 9.4. Portfolio Risk

Strategy فعلی طبق سند معماری، بک‌تست مستقل هر نماد است. این محدودیت باید صریح نمایش داده شود. تا زمانی که Portfolio Engine واقعی ساخته نشده:
- از ادعای کنترل ریسک پرتفوی چندنمادی خودداری شود؛
- همبستگی، exposure مشترک و مارجین چندنمادی به‌عنوان پشتیبانی‌شده نمایش داده نشوند؛
- sizing مبتنی بر `UNIT_APPROXIMATION` صریحاً تقریبی بماند و به lot/contract واقعی تعبیر نشود.

در فاز توسعه بعدی، Portfolio Risk باید شامل سقف ریسک تجمعی معاملات باز، همبستگی/عامل مشترک، exposure، محدودیت معاملات هم‌زمان و Max Drawdown Halt باشد. این قابلیت تا زمان وجود داده قرارداد ابزار و تست معتبر، نباید به‌عنوان کنترل واقعی معرفی شود.

## 10. قرارداد Forecast → Strategy

### 10.1. سیاست پیش‌فرض

پل Forecast به Strategy در فاز نخست فقط برای نمایش/تحلیل و پیشنهاد مشروط طراحی شود. **تنها وضعیت `VALID` با Edge اثبات‌شده می‌تواند برای بررسی ساخت سیگنال از مسیر Forecast واجد شرایط شود.** حتی در این حالت، گیت‌های مستقل Strategy و Risk/Reward باید کامل اجرا شوند.

`PROVISIONAL`، `NO_EDGE`، `INSUFFICIENT_EVIDENCE` و `DATA_NOT_READY` نباید سیگنال قابل اقدام تولید کنند. در صورت نیاز می‌توان در Research یک preview غیرقابل اجرا نشان داد، اما نباید آن را Signal معتبر نامید.

### 10.2. شرایط اجباری عبور

قبل از ارسال داده Forecast به Strategy:
- `status === VALID`؛
- `edgeStatus === PROVEN`؛
- `allowStrategy === true`؛
- symbol، timeframe، originTimestamp و horizon دقیقاً با نمودار و Strategy request تطبیق داشته باشند؛
- پیش‌بینی stale یا منقضی نشده باشد؛
- مدل و سیاست انتخاب آن پذیرفته‌شده باشند؛
- ساختار/سطوح مورد استفاده هنوز معتبر و invalidated نشده باشند؛
- مسیر و eventها provenance و نسخه داشته باشند.

سپس Strategy باید مستقل:
- ورود را بر اساس قواعد خود تعریف کند؛
- SL و TP را از ساختار معتبر تعیین کند؛
- هزینه‌های واقعی یا فرض‌های صریح را لحاظ کند؛
- Hard Gate Net R:R را پاس کند؛
- تمام قواعد anti-chase، closed-bar و duplicate را پاس کند.

اگر هر شرط fail شود، خروجی `NO_TRADE` با reason code باشد؛ نه fallback پنهان.

### 10.3. عدم وابستگی معکوس

Strategy کلاسیک نباید بدون انتخاب صریح کاربر یا policy ثبت‌شده، به Forecast وابسته شود. خرابی Forecast نباید اجرای Strategy کلاسیک مستقل را مختل کند.

## 11. Snapshot، Ledger و قابلیت بازتولید

هر اجرای Forecast باید به‌صورت immutable ثبت شود. حداقل موارد:
- شناسه اجرا؛
- symbol، timeframe، source و origin timestamp؛
- horizon و نسخه قرارداد ورودی؛
- شناسه و نسخه مدل؛
- پارامترها و سیاست AUTO؛
- نسخه Feature/Structure Engine؛
- خروجی کامل مسیر و eventها؛
- Decision Summary و reason codes؛
- hash یا fingerprint ورودی/خروجی در صورت پشتیبانی فعلی؛
- وضعیت ارزیابی و نتایج هر افق؛
- نسخه کد/Build در حدی که سیستم فعلی قابل ثبت آن است.

قواعد:
- نتیجه ارزیابی نباید Snapshot اصلی را بازنویسی کند.
- اجرای جدید باید رکورد جدید باشد.
- سررسید هر افق مستقل است.
- خطا یا ناقص بودن ذخیره‌سازی باید به کاربر/Diagnostics اعلام شود.
- Ledger محلی را با ادعای همگام‌سازی چنددستگاهی اشتباه نگیرید؛ اگر Server Sync وجود ندارد، آن را محدودیت ثبت کنید.
- داده حساس یا حجم نامحدود در LocalStorage ذخیره نکنید؛ سیاست quota و pruning باید با حفظ Snapshotهای مرجع طراحی شود.

- ادعاهای تست باید شامل نام تست، تعداد، محیط و Commit باشند.

## 15. قالب گزارش اجباری Gemini در هر تحویل

Gemini در هر مرحله باید گزارش را دقیقاً با این ساختار تحویل دهد:

1. **Scope اجراشده:** چه مواردی از همین فاز انجام شد و چه مواردی عمداً انجام نشد.
2. **فایل‌های بررسی‌شده:** مسیر فایل‌ها و دلیل ارتباطشان.
3. **فایل‌های تغییرکرده:** مسیر دقیق و خلاصه تغییر هرکدام.
4. **تصمیم‌های فنی:** دلیل انتخاب و گزینه‌های ردشده.
5. **تست‌ها:** نام دقیق، تعداد پاس/فیل، محیط اجرا؛ موارد اجرا نشده با Not Run.
6. **شواهد رفتاری:** نمونه قبل/بعد، Fixture یا خروجی قابل بازتولید.
7. **محدودیت‌ها و ریسک‌ها:** موارد حل‌نشده و اثرشان بر کاربر.
8. **مستندات:** فهرست سندهای به‌روز شده.
9. **Commit:** SHA و شاخه.
10. **وضعیت Gate:** Pass / Fail / Blocked با استناد به معیار همین سند.

گزارش‌هایی مانند «بهینه شد»، «هوشمندتر شد»، «تست‌ها پاس شدند» بدون ذکر فایل، آزمون و شواهد قابل قبول نیستند.

## 16. مواردی که قبل از پیاده‌سازی باید از کد واقعی تعیین شوند

این سند عمداً بعضی جزئیات را بدون بررسی کد قطعی نمی‌کند:

- Schema واقعی خروجی هر سه موتور اصلی و Native Registry؛
- منبع حقیقت فعلی برای statusها و انتخاب AUTO؛
- محل دقیق ذخیره و ارزیابی Snapshotها؛
- وضعیت واقعی Server Sync برای Ledger؛
- قرارداد دقیق eventهای موجود و تفاوت آن‌ها با eventهای پیشنهادی؛
- معیارهای موجود Path Quality و میزان پوشش تست؛
- وضعیت دقیق Strategy v2 و تفاوت آن با بخش‌های قدیمی `TRADING_STRATEGY_SPEC.md`؛
- مسیر واقعی TradingView data adapter و هرگونه Provider باقی‌مانده در کد؛
- ظرفیت و محدودیت‌های واقعی اجرای محاسبات در مرورگر روی موبایل/دسکتاپ.

عامل باید این موارد را در یک **Implementation Discovery Report** با ارجاع به فایل/تابع واقعی مشخص کند. حدس‌زدن نام تابع، Schema یا رفتار موجود ممنوع است.

## 17. ریسک‌ها و تصمیم‌های باز

| موضوع | ریسک | سیاست موقت |
|---|---|---|
| آستانه Strict AUTO | کاهش دلخواه باعث false winner؛ سخت‌گیری بیش از حد باعث کمبود نتیجه | آستانه‌ها را بدون تحلیل و نسخه‌بندی تغییر نده |
| تعریف Path Quality | معیارهای متعدد و هم‌بسته می‌توانند رتبه‌بندی را منحرف کنند | معیار اصلی و فرعی را از قبل ثبت کن |
| Event Detection | تشخیص پس‌نگر، look-ahead پنهان ایجاد می‌کند | زمان وقوع و تأیید جدا باشد |
| Scenario Probability | احتمال ساختگی اعتماد کاذب می‌سازد | تا کالیبراسیون معتبر، null/بدون احتمال |
| Ledger local-only | تاریخچه بین دستگاه‌ها مشترک نیست | محدودیت را شفاف نگه دار؛ Sync خارج از این فاز |
| Strategy sample size | تعداد معامله کم نتیجه را ناپایدار می‌کند | حداقل نمونه را قبل از آزمون تعریف کن |
| Portfolio sizing | مشخصات قرارداد ابزار ممکن است ناقص باشد | UNIT_APPROXIMATION را واقعی معرفی نکن |
| Runtime cost | مدل‌ها و پنل‌های زیاد مرورگر را کند می‌کنند | اجرای دستی، profiling و سقف مصرف منابع |
| Scope creep | اضافه شدن مدل/پنل قبل از اصلاح هسته | هیچ مدل جدیدی تا عبور P0 اضافه نشود |

## 18. دستور نهایی اجرای مرحله‌ای

عامل پیاده‌سازی باید به این ترتیب عمل کند:

1. ابتدا اسناد مرجع و کد شاخه اصلی را بخواند؛
2. Implementation Discovery Report را با مسیر/تابع واقعی تهیه کند؛
3. وضعیت هر بند این Master Plan را به `EXISTS / PARTIAL / MISSING / CONFLICT` نگاشت کند؛
4. فقط P0 را اجرا کند و از ورود به P1/P2/P3 پیش از عبور Gate مربوط خودداری کند؛
5. پس از هر فاز، تست و مستندات همان فاز را کامل کند؛
6. در گزارش نهایی هیچ مورد Not Run را Pass اعلام نکند؛
7. هیچ‌گاه صرفاً برای سبز شدن تست یا زیباتر شدن چارت، داده یا ساختار مصنوعی تولید نکند.

**نتیجه‌ای که از Gemini انتظار می‌رود، یک Forecast ساده‌تر اما کم‌محتواتر نیست؛ یک Forecast منظم‌تر، قابل سنجش‌تر و صادق‌تر است که بتواند رفتار مسیر را بهتر توضیح دهد و وقتی شواهد کافی ندارد، صریحاً از ادعای برتری خودداری کند.**
