# گزارش مشکلات و نقد معماری تصمیم بخش پیش‌بینی و استراتژی (`FORECAST_AND_STRATEGY_ISSUES_REPORT`)

> **نسخه مرجع:** `v1.47.41` · **تاریخ ثبت:** `2026-11-25` · **وضعیت:** `OPEN — ثبت‌شده برای حل و به‌روزرسانی در فازهای بعدی`

---

بررسی کد ریپوی `manidigit/CHART` (بهخصوص `host_subdomain/assets/js/forecast/`، `strategy/` و `forecastView.js`) انجام شد. مشکل اصلی بیشتر **طراحی محصول و معماری تصمیم** است تا چند باگ پراکنده.

## چرا اینقدر شلوغ و عملاً بلااستفاده شده؟

### ۱. هدف محصول با خروجی واقعی همخوان نیست
طبق `FORECAST_PRODUCT_FOUNDATION` هدف این است که کاربر یک **تصویر ساختاریافته و قابل ارزیابی از رفتار احتمالی قیمت** بگیرد.  
در عمل سیستم تبدیل شده به یک **آزمایشگاه تحقیقاتی مدلها**:

- ۱۰ مدل Native در Registry  
- Causal Historical Analogs  
- Structural JS  
- SMC Prediction Engine  
- Calibrated Ensemble  
- حالت `AUTO (OOS Best)`  
- بهعلاوه پنلهای Quantile Fan / Hybrid / MTF / Replay / Ledger و …

نتیجه: بهجای یک پاسخ واضح («احتمال بالا / پایین / بدون لبه» + یک مسیر اصلی)، کاربر با **ده خروجی موازی** روبهرو میشود و نمیداند کدام را جدی بگیرد.

### ۲. `AUTO` خیلی سختگیر است و اغلب برندهای انتخاب نمیکند
تابع `selectOosChartWinner` در `walkForwardEvaluator.js` برای انتخاب خودکار این شرطها را همزمان میخواهد:

- حداقل ۳۰ پنجره Outer OOS  
- \(N_{eff} \ge 25\)  
- `rMAE < 1`  
- WIS بهتر از Naive  
- Coverage 80٪ بین ۷۲–۸۸٪  
- `dmPValue ≤ 0.05` و `bootPValue ≤ 0.10`  
- مدل experimental نباشد  

اگر حتی یکی رد شود → `NO_CLEAR_WINNER_BASELINE` و نمایش `naive_persistence` (یا ensemble).  
یعنی سیستم عمداً میگوید «برندهای ندارم»، در حالی که UI همچنان پر از مدل و پنل است. این تضاد اصلی سردرگمی است: **ده مدل میبینی، ولی موتور اغلب میگوید هیچکدام برتری اثباتشده ندارند.**

### ۳. سه موتور «درجه یک» موازی بدون سلسلهمراتب تصمیم
در `forecastEngine.js` اینها همگی first-class هستند:

- Empirical Analogs (Rev 2.3)  
- Structural Wave JS (Rev 2.3)  
- SMC Prediction Engine (Rev 2.3)  
- بهعلاوه ۱۰ مدل Registry + Ensemble  

هیچ لایهٔ بالاتری وجود ندارد که بگوید:
1. اول وضعیت لبه (Edge / No-Edge)  
2. بعد یک مدل/مسیر اصلی  
3. بعد بقیه فقط برای مقایسه/پژوهش  

همه همسطح روی UI میآیند → کاربر نمیداند اولویت با کدام است.

### ۴. UI استودیو (۱۲ پنل) برای محقق نوشته شده، نه معاملهگر
`forecastView.js` حدود **۲۶۷۰ خط** است و همه چیز را همزمان نشان میدهد:

- Ladder کوانتایل  
- Conformal calibration  
- Analog medoids  
- MTF coordination  
- Event tree  
- Walk-forward table  
- Ledger با SHA-256  
- مقایسه چندمدله  

این برای ممیزی علمی عالی است؛ برای **نتیجهگیری سریع** مخرب است. جزئیات پژوهشی جلوی تصمیم را گرفتهاند.

### ۵. پیشبینی و استراتژی از هم جدا هستند (طراحی عمدی، ولی ناقص)
استراتژی فعلی (`strategy/`) عمدتاً روی **۵ استراتژی کلاسیک TA** است (Pullback، RSI، Donchian، SMA cross، …) با Hard Gate `Net R:R ≥ 2.0`.  
خروجی Forecast بهصورت پیشفرض موتور تصمیم استراتژی نیست.  
یعنی حتی اگر پیشبینی خوب باشد، مسیر واضح «پیشبینی → سیگنال → اقدام» وجود ندارد؛ دو دنیا کنار هم نشستهاند.

## باگها و نقاط ضعف واقعی بخش پیشبینی و استراتژی

| موضوع | توضیح |
|--------|--------|
| **AUTO اغلب بیفایده** | شرطهای ۶گانه خیلی سختاند؛ در داده واقعی بازار معمولاً به baseline میافتد. کاربر حس میکند AUTO کار نمیکند. |
| **Fallback پنهان به Naive** | وقتی مدل درخواستی در دسترس نباشد یا برندهای نباشد، بدون اینکه UX بهاندازه کافی «تصمیم نهایی» را برجسته کند، به `naive_persistence` برمیگردد. |
| **وضعیتهای زیاد بدون اقدام** | سلسلهمراتب `DATA_NOT_READY → INSUFFICIENT_EVIDENCE → NO_EDGE → PROVISIONAL → VALID` صادقانه است، ولی اکثر اوقات کاربر در وضعیتهای غیرقابلاقدام میماند و سیستم جایگزین تصمیم نمیدهد. |
| **مقایسه مدل بدون فیلتر تصمیم** | جدول ۱۰+ مدل حتی وقتی `NO_EDGE` است نمایش داده میشود → نویز تصمیم. |
| **Ledger فقط محلی** | طبق OPEN_ISSUES هنوز server sync ندارد؛ تاریخچه و یادگیری بین دستگاهها/جلسات محدود است. |
| **استراتژی مستقل از Forecast** | سیگنالها از TA کلاسیک میآیند، نه از مسیر پیشبینی. Forecast عملاً به Strategy وصل نشده. |
| **Hard Gate RR=2.0 خیلی سخت** | بسیاری سیگنالها `NO TRADE` میشوند؛ درست از نظر ریسک، ولی بدون خلاصهٔ قابل فهم، حس «هیچ چیز کار نمیکند» میدهد. |
| **حجم کد UI** | یک فایل ۲۶۰۰+ خطی برای استودیو نگهداری و سادهسازی UX را سخت کرده. |

باگهای حیاتی نوع crash که قبلاً در OPEN_ISSUES بودهاند (مثل `ARCH-02`، `STORAGE-QUOTA`) عمدتاً بستهشدهاند. مشکل فعلی بیشتر **قابلاستفاده نبودن برای تصمیم** است تا کرش.

## ریشه اصلی مشکل (خلاصه)

شما مدل و پنل زیاد آوردید تا **نتیجهگیری قویتر** بگیرید، ولی:

1. هیچ **لایه تصمیم واحد** بالای مدلها نگذاشتید.  
2. معیار انتخاب خودکار را آنقدر سخت گرفتید که اغلب «بدون برنده» میشود.  
3. UI پژوهشی را بهجای یک خلاصهٔ اجرایی نشان دادید.  
4. Forecast را به Strategy وصل نکردید.

نتیجه طبیعی: ده مدل، دوازده پنل، و صفر نتیجهگیری قابل اعتماد برای کاربر.

## پیشنهاد عملی برای نجات سیستم (اولویتبندی)

**فاز فوری (کمهزینه، اثر بالا):**

1. **یک کارت تصمیم اصلی** بالای همه چیز:
   - وضعیت: Edge / No-Edge / Insufficient  
   - مدل منتخب (یا صریح: «بدون برتری نسبت به Naive»)  
   - مسیر اصلی Q50 + باند ۸۰٪  
   - یک جمله دلیل انتخاب  

2. **حالتهای نمایش:**
   - `Simple` (پیشفرض): فقط تصمیم + مسیر اصلی + ۲–۳ متریک  
   - `Research`: همان ۱۲ پنل فعلی  

3. **AUTO را دو سطح کنید:**
   - سخت (فعلی) برای VALID علمی  
   - نرمتر برای «بهترین نسبی روز» تا همیشه یک انتخاب شفاف داشته باشید (با برچسب اعتماد پایین)

4. **مدلهای experimental را از مسیر تصمیم خارج کنید**؛ فقط در تب Research.

5. **یک پل Forecast → Strategy:**
   - فقط وقتی وضعیت `VALID` یا حداقل `PROVISIONAL` با Edge  
   - وگرنه صریح: «سیگنال تولید نمیشود»

بدون این لایهٔ تصمیم، اضافه کردن مدل دهم و یازدهم فقط شلوغی را بیشتر میکند.

## ۱) طرح مشخص UI و جریان تصمیم

### اصل طلایی
کاربر فقط **یک کارت تصمیم** میبیند. بقیه چیزها پشت دکمه «جزئیات / پژوهش» مخفی میشوند.

### جریان تصمیم (۴ پله، همیشه به ترتیب)

```
داده آماده؟ ──خیر──► «داده ناکافی» + چند کندل کم است
    │
   بله
    ▼
شواهد OOS کافی؟ ──خیر──► «شواهد ناکافی» + مسیر مبنا (Naive)
    │
   بله
    ▼
لبه آماری هست؟ ──خیر──► «بدون لبه» + مسیر مبنا + دلیل کوتاه
    │
   بله
    ▼
برنده OOS / مسیر اصلی ──► کارت تصمیم + باند ۸۰٪ + اعتماد
```

### صفحه پیشبینی در حالت Simple (پیشفرض)

**بالا — کارت تصمیم (همیشه ثابت):**
| بخش | محتوا |
|-----|--------|
| وضعیت | یکی از: آماده / داده ناکافی / شواهد ناکافی / بدون لبه / موقت / معتبر |
| مسیر اصلی | جهت تقریبی + Q50 افق (مثلاً ۳۰ بار) + باند ۸۰٪ |
| منبع مسیر | نام مدل منتخب یا «مبنا (Naive)» |
| اعتماد | پایین / متوسط / بالا (از همان وضعیت + coverage + edge) |
| یک جمله دلیل | مثلاً: «هیچ مدلی از مبنا بهتر نشد» یا «Analogs در OOS برنده شد» |

**وسط — فقط روی چارت:**
- یک مسیر اصلی (Q50)
- یک باند ۸۰٪
- بدون ۱۰ لایه رنگی همزمان

**پایین — حداکثر ۳ دکمه:**
1. «مقایسه مدلها» (Research)
2. «تاریخچه / Ledger»
3. «تولید سیگنال؟» (فقط اگر وضعیت ≥ موقت و Edge داشته باشد؛ وگرنه غیرفعال با توضیح)

### حالت Research (اختیاری)
همان ۱۲ پنل فعلی، ولی:
- پیشفرض بسته
- فقط وقتی کاربر آگاهانه باز کند
- برچسب واضح: «برای ارزیابی علمی، نه تصمیم روزمره»

## ۲) پیشنهاد تغییر دقیق ساختار (بدون بازنویسی کل پروژه)

### لایه جدید: Decision Layer
الان انتخاب داخل `selectOosChartWinner` + پراکندگی UI است. یک لایه میانی اضافه کن:

```
ForecastEngine.project()
        │
        ▼
buildDecisionSummary(fc)   ← جدید
        │
        ▼
{ status, primaryPath, modelId, confidence, reason, allowStrategy }
        │
        ▼
UI Simple فقط این را نشان میدهد
```

### قوانین انتخاب مسیر اصلی (پیشنهاد عملی)

| اولویت | چه زمانی | مسیر اصلی |
|--------|----------|-----------|
| 1 | کاربر دستی مدل انتخاب کرده | همان مدل (اگر موفق اجرا شد) |
| 2 | AUTO + برنده OOS سختگیر | همان برنده |
| 3 | AUTO + بدون برنده سخت، ولی یکی از ۳ مدل ترجیحی مسیر معتبر دارد | بهترینِ نسبی بین ۳ ترجیحی (با برچسب «نسبی / بدون اثبات سخت») |
| 4 | هیچکدام | `naive_persistence` + وضعیت «بدون لبه / شواهد ناکافی» |

نکته مهم: سطح ۳ را **هرگز** با سطح ۲ قاطی نکن. برچسب اعتماد باید فرق کند:
- سطح ۲ → اعتماد بالاتر + `VALID` ممکن
- سطح ۳ → `PROVISIONAL` + «برتری اثباتشده نیست»

### AUTO دو حالته
- **Strict (علمی):** همان ۶ گیت فعلی → فقط برای VALID
- **Relative (روزمره):** بین کاندیداهای غیر-experimental، کمترین WIS نسبت به Naive، حتی اگر p-value رد شود → فقط برای نمایش مسیر با برچسب اعتماد پایین

کاربر پیشفرض Relative میبیند؛ در Research هر دو گزارش میشود.

### ساختار UI فایلها (پیشنهاد)
- `forecastView.js` را نشکن، ولی رندر را جدا کن:
  - `renderDecisionCard(summary)`
  - `renderSimpleForecastView(...)`
  - `renderResearchStudio(...)` (همان پنلهای فعلی)
- پیشفرض entry point = Simple

## ۳) اولویت مدلها — وقتی نمیدانی کدام «بهتر» است

حقیقت این است: **هیچ مدل ثابتی همیشه بهتر نیست.**  
«بهتر» فقط با OOS روی همان نماد/تایمفریم/افق معنا دارد. پس اولویت را بر اساس **نقش** بگذار، نه ادعا.

### نقشها (این را در UI هم بنویس)

**الف) مسیر تصمیم (Decision pool) — فقط اینها برای مسیر اصلی**

| رتبه نقش | مدل | چرا |
|----------|-----|-----|
| مبنا | `naive_persistence` | صفر-فرض؛ اگر کسی این را نزند، ادعای لبه نداریم |
| ترجیحی ۱ | Causal Historical Analogs (`empirical_analogs`) | خود پروژه در Rev 2.3 بهعنوان یکی از ۳ ترجیحی مشخص کرده؛ علّی + embargo |
| ترجیحی ۲ | Structural JS (`structural_wave_js`) | ساختار موج/نقطه عطف؛ مناسب نمایش مسیر روی چارت |
| ترجیحی ۳ | SMC Prediction (`smc_prediction_js`) | منطق نقدینگی/ساختار SMC؛ مستقل |
| ترکیب | Calibrated Ensemble | فقط وقتی وزنهای منجمد از Walk-Forward معتبر باشند |

**ب) کاندیدای آماری سالم (میتوانند در Strict AUTO برنده شوند)**
- `kalman_momentum`
- `garch_volatility`
- `arima_ets` / `native_arima_diff`
- `historical_drift`
- `gaussian_process` (با احتیاط)

**ج) فقط Research (از مسیر تصمیم خارج شوند)**
چون در کد `isApproximation: true` دارند:
- `native_prophet_decomp`
- `native_seq_recurrent_approx`
- `native_quantile_attention_approx`

اینها را از دکمه انتخاب سریع و از AUTO سخت حذف کن؛ فقط در تب پژوهش.

### قانون طلایی اولویت
نپرس «کدام مدل بهتر است؟»  
بپرس: **«آیا کسی از Naive در OOS همین نماد بهتر است؟»**

- بله → همان برنده مسیر اصلی است (Strict)
- خیر → Naive + «بدون لبه»
- شواهد کم → Naive + «شواهد ناکافی»

سه مدل ترجیحی فقط وقتی Strict برندهای ندارد، برای مسیر «نسبی» رقابت میکنند — نه بهعنوان حقیقت علمی.

## ۴) اتصال به استراتژی (یک خط روشن)

| وضعیت تصمیم | دکمه استراتژی |
|-------------|----------------|
| VALID + Edge | فعال — «سیگنال از مسیر اصلی» |
| PROVISIONAL | فعال با هشدار اعتماد |
| NO_EDGE / INSUFFICIENT / DATA_NOT_READY | غیرفعال — متن: «بدون لبه آماری سیگنال ساخته نمیشود» |

استراتژیهای کلاسیک TA میتوانند جدا بمانند، ولی مسیر Forecast→Signal فقط از روی `primaryPath` کارت تصمیم بیاید.

## ۵) ترتیب پیادهسازی پیشنهادی (کمریسک)

1. **فقط UI Simple:** کارت تصمیم روی خروجی فعلی Engine (بدون تغییر مدل)  
2. **Decision summary object** در خروجی `ForecastEngine.project`  
3. **خارج کردن approximation از AUTO/انتخاب سریع**  
4. **AUTO Relative** کنار Strict  
5. **دکمه استراتژی شرطی**

قدم ۱ بهتنهایی بخش بزرگی از سردرگمی را کم میکند، چون دیگر ده مدل همسطح به چشم نمیآید.

---

اگر بخواهی قدم بعد را عملی کنیم، میتوانم همان **ساختار `buildDecisionSummary` + اسکلت `renderDecisionCard`** را دقیقاً روی قرارداد فعلی `forecastEngine` بنویسم (فیلدها، وضعیتها، و اینکه از کدام فیلدهای موجود `fc` خوانده شوند) تا مستقیم قابل پیاده در ریپو باشد.

## یادآوری مأموریت اصلی بر اساس اسناد بنیادین محصول (`FORECAST_PRODUCT_FOUNDATION_V1`)

برنامهٔ اصلیتان از اسناد محصول تقریباً این بود:
پیشبینی قرار نبود «ده مدل و دوازده پنل پژوهشی» باشد. مأموریت این بود که از وضعیت واقعی بازار در لحظهٔ مبدأ، یک مسیر ساختاریافته و قابل فهم روی همان چارت بسازد — نه فقط یک قیمت پایانی، یک فلش جهت، یا یک خط تزئینی. مسیر باید رفتار محتمل بازار را مدل کند (ادامه روند، اصلاح، برخورد به سطح، برگشت، رنج و …)، عدمقطعیت را فقط وقتی مبنای معتبر دارد نشان دهد، و هر اجرا ثبت و بعداً با واقعیت سنجیده شود. مدلها ابزار مقایسه و آزمایش بودند، نه خودِ هدف؛ انتخاب مدل برنده، فرمول امتیاز نهایی و جزئیات UI چندمدله عمداً باز مانده بود تا با شواهد جلو برود، نه با انباشت قابلیت.

### ۲.۱. فاصله بین مأموریت محصول و معماری فعلی

مبنای محصول بهدرستی میگوید خروجی باید رفتار آینده را مدل کند، نه صرفاً قیمت مقصد را.

اما در وضعیت فعلی، بخش قابلتوجهی از فعالیت توسعه روی این موارد متمرکز شده است:

* مقایسه مدلها.

* کالیبراسیون کوانتایلها.

* بهبود پنلهای نمایشی.

اینها ضروریاند، اما هنوز پاسخ مسئله اصلی نیستند.

پرسش اصلی این است: آیا مدل واقعاً میتواند توالی رفتار بازار را پیشبینی کند؟

مثلاً:

* به مقاومت نزدیک میشود.

* مومنتوم کاهش پیدا میکند.

* اصلاح اتفاق میافتد.

* به حمایت میرسد.

* واکنش نشان میدهد یا حمایت را میشکند.

اگر مدل فقط یک مسیر میانی بسازد که از قیمت فعلی به قیمت نهایی برسد، حتی با ثبات ریاضی عالی، هنوز مأموریت اصلی را انجام نداده است.

### ۲.۴. مسئلهای که به نظرم هنوز حل نشده: شناخت ساختار بازار

این لایه قرار نیست مدل پیشبینی دیگری باشد. وظیفه آن استخراج وضعیت قابل مشاهده بازار و تبدیل آن به اطلاعات ساختاریافته است.

نکته مهم این است که تشخیص ساختار نباید بهعنوان حقیقت قطعی وارد مدل شود. هر تشخیص باید شواهد، زمان تأیید و وضعیت اعتبار داشته باشد.

### ۲.۵. پیشنهاد مهمتر: خروجی Forecast باید رویدادمحور شود

به جای اینکه خروجی داخلی موتور فقط مجموعهای از قیمتها باشد، پیشنهاد میکنم آن را به دو بخش تقسیم کنیم:

الف) مسیر عددی

مقادیر قیمت در افقهای زمانی مختلف، کوانتایلها و در صورت وجود سناریوهای معتبر.

ب) رویدادهای ساختاری

| رویداد             | اطلاعات موردنیاز            |
| ------------------ | --------------------------- |
| Trend Continuation | جهت و بازه زمانی            |
| Resistance Test    | محدوده قیمت و زمان احتمالی  |
| Pullback           | عمق و مدت اصلاح             |
| Reversal           | محدوده چرخش و شواهد         |
| Breakout           | سطح شکست و شرایط تأیید      |
| Support Reaction   | محدوده واکنش و سناریوی شکست |
| Range Formation    | مرزهای محدوده و مدت احتمالی |

این رویدادها باید به مسیر عددی متصل باشند، نه اینکه جداگانه توسط یک متنساز تولید شوند.

برای مثال، اگر سیستم پیشبینی کرده است که قیمت ابتدا به مقاومت برسد و سپس اصلاح کند، باید این اتفاق در مختصات زمانی و قیمتی مسیر نیز قابل مشاهده باشد.

این ویژگی محصول را از یک Forecast Line به یک Market Behavior Forecast تبدیل میکند.

### ۲.۶. عدمقطعیت باید به رفتار سناریوها متصل شود

من با رویکرد فعلی اسناد درباره عدمقطعیت موافقم؛ یعنی احتمال ساختگی ممنوع باشد.

اما پیشنهاد میکنم از مفهوم یک باند ساده بالایی و پایینی فراتر برویم.

سه وضعیت قابل بررسی:

* Base Path: مسیر اصلی مدل.

* Alternative Path: مسیر جایگزین با شرایط وقوع مشخص.

* Invalidation Zone: محدودهای که با عبور از آن، فرض ساختاری مسیر دیگر معتبر نیست.

مثلاً:

* مسیر اصلی: ادامه صعود تا مقاومت.

* سناریوی جایگزین: شکست حمایت و ادامه اصلاح.

* نقطه ابطال: عبور معتبر از محدودهای که فرض روند صعودی را نقض میکند.

اینها نباید بهصورت سه پیشبینی مستقل و دلخواه ساخته شوند. باید از مدل یا روش آماری دارای شواهد به دست آیند.

### ۳.۱. وضعیت فعلی Strategy

### ۳.۲. Hard Gate برابر 2.0 نباید بهتنهایی معیار کیفیت استراتژی باشد

من با جلوگیری از معاملات دارای نسبت ریسک به بازده ضعیف موافقم.

اما یک خطر وجود دارد: نسبت R:R بالا لزوماً به معنای معامله خوب نیست.

برای مثال:

| ویژگی               | استراتژی A | استراتژی B |
| ------------------- | ---------- | ---------- |
| Net R:R             | 2.0        | 3.0        |
| Win Rate            | 60٪        | 30٪        |
| امید ریاضی بر حسب R | +0.80      | +0.20      |

با فرض سادهسازی و بدون در نظر گرفتن هزینههای اضافی، استراتژی A با وجود R:R پایینتر، امید ریاضی بالاتری دارد.

بنابراین:

* Hard Gate میتواند یک سیاست محافظهکارانه باقی بماند.

* اما نباید آن را معادل کیفیت آماری استراتژی بدانیم.

* باید Expectancy، Drawdown، توزیع نتایج و پایداری OOS نیز در تصمیم دخالت کنند.

همچنین بهتر است حداقل R:R در سطح سیاست ریسک تعریف شود، نه اینکه در آینده همه استراتژیها الزاماً با یک عدد ثابت و بدون امکان ارزیابی تجربی سنجیده شوند.

### ۳.۳. بکتست فعلی برای پذیرش استراتژی کافی نیست

تفکیک 70/30 برای In-Sample و Out-of-Sample شروع مناسبی است، اما بهتنهایی کافی نیست.

مشکلات:

* یک تقسیم زمانی ممکن است بهشدت تحت تأثیر یک رژیم خاص بازار باشد.

* آزمایش چندین استراتژی و پارامتر روی یک بخش OOS باعث انتخابگری آماری میشود.

* عملکرد خوب روی یک نماد، تضمین عملکرد روی نماد دیگر نیست.

* همزمانی چند سیگنال و ریسک تجمعی پرتفوی فعلاً پوشش کامل ندارد.

پیشنهاد من:

Purged Walk-Forward + Embargo + Final Untouched Holdout

یعنی:

* آموزش و تنظیم پارامترها فقط در بازه گذشته.

* حذف نمونههای دارای همپوشانی اطلاعاتی.

* فاصله حفاظتی میان دادههای آموزش و ارزیابی.

* ارزیابی روی پنجرههای متوالی.

* نگهداری یک مجموعه نهایی که تا زمان پذیرش استراتژی دستنخورده بماند.

این روش باید قبل از معرفی یک استراتژی بهعنوان برنده اجرا شود.

### ۳.۴. محدودیت جدی در مدیریت ریسک پرتفوی

طبق مستندات، شبیهساز فعلی هر `chart_id` را مستقل ارزیابی میکند.

یعنی ممکن است سه استراتژی روی سه نمودار جداگانه، هر کدام ریسک مجاز خود را داشته باشند، اما مجموع ریسک آنها برای یک حساب معاملاتی بیش از حد شود.

مواردی که هنوز نیازمند طراحی هستند:

* سقف ریسک کل معاملات باز.

* همبستگی نمادها.

* Exposure مشترک.

* Max Drawdown Halt.

* محدودیت تعداد معاملات همزمان.

* ریسک تجمیعی داراییهای همجهت.

این موضوع برای توسعه آینده بسیار مهم است.

همچنین محدودیت اندازه قرارداد و محاسبه حجم در بعضی نمادها به تقریب واحدی متکی است. این موضوع باید مانع استفاده از Position Sizing بهعنوان مقدار واقعی قابل معامله شود.

### ۴. پیشنهاد معماری نهایی من برای آینده محصول

به نظرم باید سه لایه را از هم تفکیک کنیم:

لایه اول

Market Intelligence

شناخت وضعیت فعلی بازار، ساختار قیمت، روند، نواحی مهم، نقدینگی، سشن و رژیم بازار.

لایه دوم

Forecast Intelligence

تولید مسیر آینده، نقاط چرخش، اصلاحها، سناریوها، محدودههای عدمقطعیت و ارزیابی تاریخی.

لایه سوم

Trading Strategy Intelligence

تبدیل تحلیل بازار و در آینده Forecast معتبر به تصمیم معاملاتی، ورود، خروج، SL، TP و مدیریت ریسک.

این سه لایه باید بتوانند اطلاعات استاندارد با یکدیگر مبادله کنند، اما هیچکدام نباید مسئولیت دیگری را تصاحب کند.

مثلاً شکست Forecast نباید باعث تولید سیگنال معاملاتی ساختگی شود. همچنین وجود یک سیگنال کلاسیک نباید به معنای تأیید مسیر پیشبینی باشد.

### ۵. نقشه راه پیشنهادی به ترتیب اولویت

من پیشنهاد نمیکنم در این مرحله مدل جدیدی اضافه کنیم. ابتدا باید کیفیت خروجی مدلهای موجود را اثبات کنیم.

P0 — اولویت بحرانی

اول انجام شود

۱. تکمیل معیار پذیرش مسیر پیشبینی

* تعریف امتیاز مستقل برای Path Quality.

* سنجش سقفها، کفها و نقاط چرخش.

* سنجش عمق و مدت اصلاح.

* سنجش تشخیص تغییر روند و رنج.

* مقایسه با Naive Baselines.

* ارزیابی جداگانه هر نماد، تایمفریم و رژیم بازار.

P1 — اولویت بسیار بالا

مرحله بعد

۲. تکمیل Market Structure & Behavior Engine

* استخراج ساختار بازار بهصورت علّی.

* تشخیص روند، رنج، شکست و اصلاح.

* استخراج نواحی حمایت و مقاومت.

* تعیین شواهد و اعتبار هر تشخیص.

* ارائه زمینه استاندارد به مدلهای Forecast.

۳. تکمیل Forecast Scenario Engine

* مسیر اصلی و جایگزین.

* نقاط احتمالی برگشت.

* محدودههای ابطال سناریو.

* اتصال رویدادهای ساختاری به مختصات مسیر.

* کالیبراسیون عدمقطعیت بر مبنای داده واقعی.

P2 — اولویت بالا ۴. ارتقای Model Governance

* جلوگیری از نشت داده در انتخاب AUTO OOS Best.

* تعریف Final Holdout مستقل.

* مقایسه مدلها با شرایط کاملاً یکسان.

* ثبت نسخه مدل، داده و تنظیمات.

* تعریف معیار پذیرش و تنزل مدل.

۵. ارتقای Strategy Validation

* Purged Walk-Forward.

* Embargo.

* بررسی پایداری استراتژی.

* آزمون حساسیت هزینه.

* ارزیابی ریسک پرتفوی و معاملات همزمان.

* تکمیل مشخصات واقعی قرارداد و اندازه معاملات.

P3 — توسعه بعدی ۶. ارتباط کنترلشده Forecast و Strategy

* امکان استفاده از سناریوهای معتبر Forecast در Strategy.

* مقایسه استراتژی مبتنی بر پیشبینی با استراتژی کلاسیک.

* ارزیابی ارزش افزوده Forecast در تصمیم معاملاتی.

* عدم اجازه استفاده از Forecastهای Provisional یا فاقد شواهد کافی.

### ۷. تصمیم پیشنهادی من

اگر مسئول تعیین مسیر توسعه این پروژه بودم، فعلاً این تصمیمها را قطعی میکردم:

* توسعه مدل جدید متوقف شود تا مدلهای موجود ارزیابی شوند.

* سه مدل اصلی Analog، Structural و SMC در اولویت پذیرش قرار بگیرند.

* معیار موفقیت Forecast از دقت قیمت نهایی به کیفیت کل مسیر ارتقا پیدا کند.

* Strategy مستقل بماند، ولی قرارداد ارتباطی آینده آن با Forecast مشخص شود.

* هیچ مدل یا استراتژی صرفاً با پاس شدن تست نرمافزاری، برنده اعلام نشود.

مهمترین توصیه من: اکنون زمان توسعه قابلیتهای بیشتر نیست؛ زمان اثبات این است که قابلیتهای ساختهشده واقعاً ارزش تحلیلی دارند.
